> 本文件記錄各功能的設計邏輯與實作決策，供日後維護與改版參考。
> 最後更新：v1.1.1

## 一、資料目錄（絕對不要改 APP_NAME）

```
APP_NAME          = "CS2ChatTranslator"   ← 資料目錄名，永遠不變
APP_DISPLAY_NAME  = "全球通"               ← 對外顯示名，可自由改
user_data_dir()   = %APPDATA%\CS2ChatTranslator
```

**為什麼要解耦**：`APP_NAME` 決定 `config.json`、`secrets.json`（API Key）、
`memory.db`（翻譯記憶／術語庫）放哪裡。若改產品名時順手把 `APP_NAME` 也改了，
程式會跑去一個**全新的空目錄**，使用者的資料全部變成孤兒 —— 體感就是「資料全沒了」。

> 真實事故：v1.1.0 發布時 `APP_NAME` 被改成 `"QuanQiuTong"`，
> 使用者的 153 條術語、61 條快取、139 條歷史全部「消失」（其實還在舊目錄）。
> v1.1.1 已修回，並加了 `TestDataDirStability` 防止再犯。

**改版檢查清單**：改產品名時，只改 `APP_DISPLAY_NAME`；`APP_NAME` 不動。

## 二、實時翻譯頁：消息排列與自動滾動

### 兩種模式（設定 → 消息排列）

| 模式 | 行為 | 適用 |
|---|---|---|
| **最新在底部**（預設） | 新消息追加在尾端，自動滾動到底 | 習慣聊天軟體的人 |
| **最新在頂部** | 新消息插在 `row 0`，永遠第一眼看到 | 不想被滾動問題干擾 |

### 自動滾動的關鍵設計

**錯誤做法**（v1.1.0）：
```python
# 每次都現算「是否在底部」
at_bottom = bar.value() >= bar.maximum() - 4
```
問題：消息剛插入時**滾動條範圍還沒更新**，`maximum` 還是舊值，
於是「其實還在底部」被誤判成「已離開底部」→ 自動滾動從此失效，
而且一旦失效就再也不會恢復。使用者感受就是「有新消息必須手動往下滑」。

**正確做法**（v1.1.1）：
```python
# 用旗標追蹤「使用者的意圖」，不現算
self._user_scrolled_away = False   # 使用者是否主動往上翻

def _on_scroll(self, value):
    # 只有使用者真的動了滾動條才更新旗標
    self._user_scrolled_away = ...
```

**設計原則**：
- 使用者在底部 → 新消息自動跟著滾，並隱藏「回到最新」按鈕
- 使用者主動往上翻 → **不強制拉回**（尊重閱讀），顯示「↓ 回到最新」按鈕
- 使用者按按鈕或自己滾回 → 恢復自動滾動

### 上限淘汰（`match_message_limit`，預設 300）

淘汰的永遠是**最舊**那一端，方向隨排列模式而異：

| 排列 | 新消息插入位置 | 淘汰位置 |
|---|---|---|
| 最新在底部 | `append` 到尾端 | 刪除開頭（`[0:overflow]`） |
| 最新在頂部 | `insert` 到 `row 0` | 刪除尾端（`[-overflow:]`） |

### 切換排列不丟資料

`set_newest_first()` 用 `_rows.reverse()` 反轉現有資料，
**不重建、不重新查詢**，所以切換是瞬間的且內容完整保留。

## 三、詞彙表效能（O(n²) 陷阱）

**症狀**：打開詞彙表很卡，反覆切換越切越慢（14ms → 3568ms）。

**根因**：欄位用 `QHeaderView.ResizeToContents` 自動貼合內容時，
Qt 會在**每一個 `setItem` 之後**重算欄寬。153 列 × 6 欄就退化成 O(n²)：

| 做法 | 153 列重建耗時 |
|---|---|
| 邊填邊算（原本） | **1317 ~ 3178 ms** |
| 重建期間隱藏表格 + 最後只算一次 | **8 ~ 14 ms** |

**修法**：
```python
was_visible = table.isVisible()
table.setVisible(False)      # 讓 Qt 延後排版
...填資料...
table.setVisible(was_visible)
table.resizeColumnsToContents()   # 只算一次
```

**其他配套**：
- 搜尋框加 180ms 延遲（`_search_timer` 單次觸發），不是每按一鍵就重建
- 統計改用 `term_stats()` SQL 聚合（0.025ms），
  取代 `list_terms(limit=100000)` 撈進 Python 逐筆數

## 四、三層資料保留

| 層級 | 內容 | 新開一局 | 重啟程式 |
|---|---|---|---|
| 當前局消息 | `match_messages`（上限 300） | 清空 | 清空 |
| 歷史對局 | `matches` + 歷史訊息 | 保留 | 依 `history_match_limit` 保留最近 N 局 |
| 長期記憶 | `translation_memory` / `translation_terms` / `translation_templates` | **保留** | **保留** |

**啟動重置**（`reset_on_startup=True`，預設開）：
清空實時翻譯與歷史對局，**只保留長期快取與詞彙表**，
並把 console.log 讀取位置重設到檔案末尾（`read_history_on_start=False`），
避免把上次遊戲的舊訊息當新訊息翻譯。

## 五、查詢順序（避免浪費 API 費用）

翻譯一句話時，依序查找，命中就回傳、**不呼叫 API**：

```
1. 人工修正（優先級最高，AI 結果不可覆蓋）
2. 長期記憶（完全相同的句子）
3. 術語庫（詞邊界匹配，拉丁詞不拆詞；CJK 用子串）
4. 句式模板（可代入數字，如 "3 enemies left" → "还剩 3 个敌人"）
5. 共用快取
6. 才呼叫 API
```

**快取鍵** = `(source_hash, target_language, direction, cache_version)`
→ 同一句話翻成英文與俄文是**兩筆獨立快取**，方向也隔離。

**失敗不寫快取**：`NetworkError` / `AuthError` / `EmptyResponseError`
一律不寫入，避免把錯誤結果永久固化。

## 六、對局隔離

- 每局有獨立 `match_id` 與 `generation` 計數器
- 換局時 `generation` 遞增，**遲到的翻譯結果**比對 generation 後丟棄
- 待處理任務被取消，訊息上下文清空
- 連續重複的地圖載入會被去重（真實日誌曾出現同張圖載入 3 次）

**對局訊號**（來自真實日誌，未經多局驗證）：
- 開始：`[HostStateManager] Host activate: Loading (<map>)`
- 結束：`Idle (levelload)` / `Quitting`

`auto_match_detection` 預設 **False**，UI 標示「信號未驗證」。

## 七、中文回覆三態（不自動發送）

嚴格區分三個狀態，**絕不虛報已發送**：

```
初始      → '等待翻译'
翻譯返回  → '① 译文已生成（尚未复制）'
點複製    → '② 已复制到剪贴板（尚未发送）'
勾選確認  → '③ 已确认在游戏中发送'      ← 由使用者手動勾選
重新翻譯  → 退回 ①（確認框自動重置）
取消確認  → 退回 ②
失敗      → 退回 '等待翻译'，草稿保留
```

**設計約束**：不注入、不 Hook、不讀記憶體、不修改遊戲檔案、不模擬按鍵。
因此無法自動發送 —— 使用者在遊戲內正常貼上並發送後，再回來勾選確認。

## 八、Trusted Mode 合規性（官方依據）

Valve 官方 Trusted Mode FAQ 明確指出：

- Trusted mode **blocks third-party files from interacting with the game**
- **沒有白名單** —— 「in Trusted mode, all foreign software is blocked」
- 注入會被 VAC 封鎖；未簽章 DLL 注入會進入 insecure mode，**無法在 VAC 安全伺服器遊玩**
- 唯一出口是 `-allow_third_party_software`，但那等於**關閉 Trusted Mode**

**本專案的做法**：只**讀取** `console.log`（遊戲側只寫的日誌檔案），
在遊戲外的程式視窗顯示翻譯。**完全不與遊戲程序互動**，
因此不觸發 Trusted Mode 任何限制，使用者也**無需關閉 Trusted Mode**。

**第一階段結論**：原生聊天 HUD 顯示外部文字**沒有受支持的實現方式**。
`say` 指令雖存在，但外部觸發必經模擬輸入或注入，兩者皆在禁止範圍。

## 九、Windows 特定實作

| 問題 | 解法 |
|---|---|
| `open()` 無 `FILE_SHARE_DELETE`，會擋住 CS2 刪除日誌（WinError 32） | 用 `CreateFileW` 帶 `FILE_SHARE_READ\|WRITE\|DELETE` |
| 原生標題欄在深色主題下仍是白色 | `DwmSetWindowAttribute`：`DWMWA_USE_IMMERSIVE_DARK_MODE`=20、`CAPTION_COLOR`=35、`TEXT_COLOR`=36 |
| 主控台輸出非 UTF-8 導致 `UnicodeEncodeError` | `_make_console_output_safe()`（UTF-8 + errors="replace"） |
| `config.json` 帶 BOM 導致 `json.loads` 失敗 → 靜默回退預設值 | `_read_config_data()` 容忍 BOM |
| `QBuffer(QByteArray())` 臨時物件被 GC → 存取違規 `0xC0000005` | 保持引用 |

## 十一、打包與發布

```powershell
# 1. 打包（注意：要從 workspace 的 stage 目錄建，assets/ 會被沙箱擋）
python cs2-build/stage_project.py
cd cs2-build/stage
python -m PyInstaller cs2-build/global_onefile.spec --clean

# 2. 安裝到桌面
Copy-Item cs2-build/global_dist/全球通.exe C:\Users\God\Desktop\

# 3. 驗證
全球通.exe --version
全球通.exe --diagnose <console.log 路徑>
```

**發布注意事項**：
- GitHub Release 資產**不支援中文檔名**（回 `Invalid name for request`），
  要用 ASCII 檔名（`QuanQiuTong-v1.1.1.exe`），中文名放進 `label`
- 大檔（>50MB）上傳用 `curl`（urllib 在代理環境會被 SSL 中斷）
- `.gitignore` 必須攔住 `secrets.json` 與 `memory.db`
